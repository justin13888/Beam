## Outcome

Opening the Android app with a stored session lands the viewer signed in, without a network round trip, as `beam-client-core` documents. A `401` on that restored cookie, or on any later call, withdraws the cookie everywhere and returns the viewer to sign-in. Both behaviours are pinned by tests on each side of the UniFFI boundary.

## Findings

- **core-IMPL-003** `beam-client-core/src/ffi.rs:2060-2066`. `install` says "A restored cookie is trusted until a request says otherwise, which is what keeps a cold start off the network". The state it then sets for a restored cookie is `SessionState::Expired`, and no success path moves `Expired` to `Authenticated`: `send` (`ffi.rs:2409-2418`) changes no state on `Ok`, and `SessionEvent::StoredSessionRestored` is never sent. The test `a_restored_session_is_expired_until_a_request_confirms_it` (`ffi.rs:2715`) asserts only `Expired`.
- **android-TEST-001** `beam-android/app/src/main/kotlin/dev/beam/android/MainViewModel.kt:59-69`. `isSignedIn = session is SessionState.Authenticated`, computed from `restore()`. Every cold start therefore shows sign-in. `Fixtures.server` (`beam-android/core/testing/.../Fixtures.kt:246`) restores servers as `Authenticated`, which the real core never does, so no Android test sees it. `MainViewModelTest` asserts only `isAdmin`.
- **core-TEST-001** `beam-client-core/src/session.rs:189-197, 225`. A `401` from `Expired` falls through to `(current, _)` with no effects, so the rejected cookie stays registered and stored. The only 401 test starts from a signed-in client (`ffi.rs:3979`).
- **android-TEST-002** `beam-android/core/ffi/.../BeamErrors.kt:16`. No production code reads `BeamFailure.requiresSignIn`. The back stack is chosen once (`BeamApp.kt:62`), so a session expiring mid-use never returns the viewer to sign-in.
- **core-TEST-012** `beam-client-core/src/session.rs:389`. `every_state_and_event_pair_terminates_without_panicking` asserts nothing (`let _ = transition(..)`), and the transitions above are unpinned.

## Decisions taken

These are the run's decisions under the autonomy contract. Nobody has reviewed them.

1. Which reading of the restored-session contract is right: the doc ("trusted until a request says otherwise") or the code (`Expired`).
   Taken: the doc. A restored cookie reads as signed in, and the first `401` withdraws it. The maintainer requires a daily-usable Android app, and signing in again on every cold start fails that.
   Rejected: the code. Keeping `Expired` and correcting the docs makes every cold start a sign-in. The ffi.rs comment records the intent the other way.
   Reverses: keep `SessionState::Expired` on restore, rewrite the two doc comments, and route Android to sign-in on `Expired`.
2. How the restored state is represented. The lane chooses: an `Authenticated` built from the stored identity, a distinct `Restored` state Android treats as signed in, or `StoredSessionRestored` applied on install. Whichever it picks must keep the cold start off the network and must be recorded in the PR.

## Surface

This changes the session-state contract the UI sees across UniFFI (`SessionState` on restore) and Android's cold-start routing. Every caller is in this repository: Android, and Apple's `beam-apple` consumer of the same `SessionState`, whose behaviour must be kept or adjusted in the same PR. Nothing is published.

## Constraints

- No gate is weakened. Fixtures must mirror the core's real restore state rather than an idealised one.
- No change is made to any other observable surface; one found to be needed is filed as a new issue.

## Tests the PR adds

- core: `a_401_on_a_restored_cookie_withdraws_it_everywhere`, `a_restored_session_is_usable_without_a_request`, and `a_late_identity_confirmation_after_logout_does_not_sign_in`. The exhaustive transition loop asserts invariants (`ClearCookie` implies `InstallCookie(false)`).
- Android: `a_stored_session_starts_signed_in`, `a_restore_that_fails_is_ready_and_signed_out`, and `a_session_expiring_mid_use_returns_to_sign_in`.
