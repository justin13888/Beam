## How to read this page

Every failure is an **RFC 9457 problem document**, served as
`application/problem+json`, on every endpoint and for every status:

```json
{
  "type": "https://beam.justinchung.net/reference/errors/#source-file-missing",
  "title": "Source file missing from disk",
  "status": 404,
  "detail": "Source video file not found"
}
```

- **`type` is the contract.** It is a stable, machine-readable identifier, and it is the thing to
  branch on. Each one links to a section below.
- **`status` is the contract.** It agrees with the HTTP status line.
- **`title` is a fixed summary** of what the `type` means. It does not vary between occurrences.
- **`detail` is not a contract.** It is a sentence for a person reading devtools or a log. It
  changes without notice, and it often interpolates an internal message. Do not parse it, match on
  it, or show it to a user without deciding first whether it reads as an explanation.

`type` may also be **`about:blank`**, which RFC 9457 defines as "the status code is the whole
story". Beam returns it wherever no finer distinction exists — see [Responses with no
code](#responses-with-no-code).

<Aside type="note" title="One shape, everywhere">
Earlier releases answered with three different body shapes chosen by *which endpoint you called* —
a JSON `{"error": "…"}` envelope, bare `text/plain`, and a nested object from the web framework for
an unmatched route — and carried no machine-readable identifier at all. All of that is gone. One
type deserialises every failure Beam can produce, including those the framework answers directly.
</Aside>

## Codes

Each heading is the code exactly as it appears after the `#` in `type`.

### media-not-found

**404.** No movie or show has this id.

**What to do.** Check the id. A title can also disappear between a browse and a detail request if a
rescan removed it, in which case reloading the list is the right response.

### invalid-media-id

**400.** The media id in the path is not a UUID.

**What to do.** Fix the caller. Every route taking a media id — the detail route, `/sources`, the
admin refresh, and `/v1/artwork/{kind}/{id}/{variant}` — answers this, so they all agree. `GET
/v1/media/{id}` and the artwork route used to answer [`media-not-found`](#media-not-found) and
[`artwork-not-found`](#artwork-not-found) here instead, because each resolved the id through a lookup
that could not tell "malformed" from "absent".

### sources-not-available-for-show

**400.** Sources were requested for a *show* id. A show has no files of its own.

**What to do.** Ask for the sources of one of its episode ids. An episode that has no files yet is
not this error — it returns an empty list.

### library-not-found

**404.** No library has this id.

### invalid-library-id

**400.** The library id in the path is not a UUID.

### library-path-not-found

**400.** The library root does not resolve to a directory on the server: it does not exist, it could
not be resolved, or it resolves to something that is not a directory — a media file rather than the
folder holding it, most often. Registration and rescan apply the same *directory* rule, so a root
that fails it cannot be registered and, if it was registered before it changed, cannot be scanned.
Registration applies two further rules a rescan does not: the root must resolve inside the
configured video directory (which fails as [library-path-outside-root](#library-path-outside-root)
instead), and the video directory itself must be readable.

This code also covers one condition that is **not** about the path you sent: if `BEAM_VIDEO_DIR`
itself cannot be resolved, every attempt to register a library answers with it, whatever path was
requested. Tell the two apart by the `detail` — `Video directory is not accessible` names the
server's own configuration, while `Library path does not exist` and `Library root path is not a
directory` name what you asked for.

**What to do.** The path is resolved **on the server**, not on the machine running the request.
Check that a *directory* by that name exists inside the container and that the bind mount is
present. A rescan can also raise this if the root has gone — or been replaced by a file — since the
library was registered. If the `detail` names the video directory, the requested path is not the
problem: check that `BEAM_VIDEO_DIR` points at a directory that exists in the container and that its
mount is present.

A library already registered against a path that has since become a regular file cannot be repaired
in place — there is no update-library endpoint — so it has to be deleted and registered again.

A rescan also answers with this code when the root **is** a directory but holds no video files Beam
can index — no file with one of the [indexed extensions](/operate/libraries/#which-files-get-indexed)
anywhere beneath it — while the library still has video files indexed. The `detail` reads `Library
root contains no video files but video files are indexed; refusing to reconcile`. An unmounted
volume usually leaves its mount point behind empty, or holding only files such as `.not_mounted`,
`.DS_Store` or `Thumbs.db`, and believing that walk would mark every indexed file missing — and,
once the grace period ran out, purge them with everyone's progress — so Beam refuses the scan and
changes nothing. The admin notification names the library,
how many video files are indexed, and the root. The Logs tab entry's message names the library and
that count; the root is in the entry's **Details** (`path`), alongside `library_id` and
`indexed_video_files`. Check the mount inside the container and rescan once the files are visible
again. If you really did remove every video on purpose, delete the library instead.

### library-path-outside-root

**400.** The root path resolves outside the directory Beam is permitted to serve from.

**What to do.** Put the library under `BEAM_VIDEO_DIR`, or widen that setting. The check follows
symlinks and `..` before deciding, so a path that *looks* contained can still fail this — which is
the point.

### library-path-overlaps-library

**409.** The root is the same directory as an existing library's root, lies inside one, or contains
one. Registering it would index the same files twice, as two libraries with two sets of rows, so the
request conflicts with a library that already exists. The comparison is by whole path components
after symlinks and `..` are resolved: `/videos/movies` overlaps `/videos/movies/4k` but not
`/videos/movies2`. The `detail` names neither path; the server log does.

**What to do.** Register a directory that is disjoint from every existing library, or delete the
library it overlaps first — for example, replace `/videos/movies` and `/videos/movies/4k` with one
library at `/videos/movies`.

### library-path-overlaps-data-dir

**400.** The root is the server's data directory (`BEAM_DATA_DIR`), lies inside it, or contains it.
The data directory holds Beam's own state, which it writes to — a library must be read-only to Beam,
and indexing Beam's artwork cache as media is never what was meant. The `detail` names neither path.

**What to do.** Keep `BEAM_DATA_DIR` outside every library root. With the Compose file, `/data` and
`/videos` are separate mounts, so this only arises when one is configured inside the other.

### user-not-found

**404.** No user has this id.

### cannot-disable-self

**400.** An administrator tried to disable their own account.

**What to do.** Have another administrator do it. This exists so the last administrator cannot lock
everyone out of the server.

### file-not-found

**404.** No file has this id.

### source-file-missing

**404.** The file *is* in the catalogue. The path it names is not on disk.

**What to do.** This one is an operator's problem, not a viewer's, and no amount of retrying will
change it: Beam's catalogue and your storage have diverged. A bind mount is missing, the library
moved, or the file was deleted outside Beam. Check the mount first, then rescan the library.

It is deliberately distinct from [`file-not-found`](#file-not-found), which means the catalogue
never had the file. A client that shows both as "not found" tells the viewer to go looking for
something they cannot fix.

### artwork-not-found

**404.** No image for this title.

Three conditions share this code: the title's row carries no artwork URL, the variant does not apply
to that kind (a season has no backdrop, an episode has no poster), or the provider no longer serves
the image enrichment recorded.

**What to do.** Nothing. This is the ordinary case, not a fault -- draw your placeholder. It is
deliberately *not* [`source-file-missing`](#source-file-missing): a title without a poster says
nothing about whether its video file is on disk, and telling a viewer to ask an administrator to
rescan the library because a show has no backdrop sends them after a problem that does not exist.

Beam remembers a failed upstream fetch for a short while, so a grid of clients does not re-ask a
dead provider once per render.

### artwork-upstream-failed

**502.** Beam asked the provider for the image and could not use what came back.

The provider returned a non-image content type, a body over the configured ceiling
(`BEAM_ARTWORK_MAX_IMAGE_BYTES`), an unhappy status, or nothing at all.

**What to do.** Retry later, and draw the placeholder meanwhile. A 502 rather than
[`internal`](#internal) because the fault is not Beam's -- `internal` means Beam broke, and
reporting a provider CDN timeout that way tells an operator to go looking in the wrong place. The
converse holds too: a stored artwork URL that Beam *itself* refuses to fetch (not `https`, or
unparseable) is reported as [`internal`](#internal), because no request was ever made and the bad
data is Beam's own.

### invalid-file-id

**400.** The file id in the path is not a UUID.

Only from the delivery routes — `/v1/files/{id}/stream` and `/download`. `PUT
/v1/files/{id}/progress` takes the same parameter but answers a malformed one with `about:blank`
and no code: its id is typed as a UUID, so the framework rejects it before Beam sees it, and a
framework rejection carries no type Beam can name. The delivery routes take theirs as a string
precisely so this code can exist there.

### login-attempt-invalid

**400.** From `/v1/auth/callback`. The round-trip cannot be matched to one this server started: the
state cookie or the state parameter is missing, the two disagree, the pending record was already
used or has expired, or the authorization code is absent.

**What to do.** Start again from the app. This is nearly always a stale or replayed sign-in — the
callback URL is single-use, so reloading it fails by design. If it happens *every* time, the
browser is dropping the short-lived state cookie: check third-party cookie blocking, and that
`BEAM_COOKIE_SECURE` matches your scheme.

One code covers all five conditions deliberately. A caller does the same thing for each of them,
and naming which half of a CSRF check failed tells an attacker more than it tells a user.

### login-failed

**400.** From `/v1/auth/callback`. The identity provider returned an error, or the token exchange
did not verify.

**What to do.** Read the server log for the provider's own message. A nonce mismatch here usually
means two sign-ins raced in the same browser.

### account-disabled

**403.** The identity verified, and the local account is disabled. No session is created.

**What to do.** An administrator re-enables the account.

### oidc-unavailable

**503.** From `/v1/auth/login`. Beam could not start a sign-in flow.

**What to do.** Beam needs `BEAM_OIDC_ISSUER`, `BEAM_OIDC_CLIENT_ID` and `BEAM_OIDC_CLIENT_SECRET`
**all three** set, and must be able to reach the issuer's `.well-known/openid-configuration`. This
is a 503 rather than a 500 because the server is working and the identity provider is not.

### account-removed

**401.** From `/v1/me`. The session is valid and the account behind it no longer exists.

**What to do.** Sign in again. This is distinct from an ordinary 401 because the session was not the
problem.

### invalid-session-id

**400.** The session id in the path is not a UUID.

Only `DELETE /v1/sessions/{id}` can produce it. Until the taxonomy landed this condition was a
**500**: the handler flattened every store error into `internal`, so a client's own typo came back
as "Beam broke" and the 400 the operation advertised had nothing that could reach it.

**What to do.** Send an id from `GET /v1/sessions`. Distinct from
[`session-not-found`](#session-not-found), which means the id was well-formed and named no session
of yours -- retrying that one with the same id will never work either, but for a different reason.

### session-not-found

**401.** From `DELETE /v1/sessions/{id}`. No such session.

**What to do.** Nothing. A session id that does not exist and one belonging to somebody else answer
identically and deliberately, so that this endpoint cannot be used to enumerate other people's
sessions.

### malformed-origin

**403.** The `Origin` or `Referer` header could not be parsed.

**What to do.** Usually a reverse proxy rewriting the header. See
[`cross-origin-rejected`](#cross-origin-rejected).

### cross-origin-rejected

**403.** A state-changing request carried an `Origin`/`Referer` that is not allowed.

**What to do.** The value must match `BEAM_WEB_URL`, `BEAM_SERVER_URL`, or an entry in
`BEAM_EXTRA_ALLOWED_ORIGINS`. The usual causes are a reverse proxy rewriting the header and reaching
Beam on a hostname it was never told about. A request carrying *neither* header is allowed through —
non-browser clients send neither, and `SameSite=Lax` on the session cookie is what actually stops
the browser case.

### admin-required

**403.** An administrator-only endpoint -- anything under `/v1/admin` -- was called by a signed-in
user who is not an administrator.

**What to do.** Fix the admin claim at your identity provider, then **sign out and back in**: admin
is recalculated only at sign-in, so a session that began before the claim changed keeps the old
answer.

### rate-limited

**429.** The client spent its request budget for this class of endpoint.

Carries **`Retry-After`** in seconds, plus `X-RateLimit-Limit`, `-Remaining` and `-Reset`.

| Class | Endpoints | Default |
|---|---|---|
| Auth | `/v1/auth/login`, `/v1/auth/callback` | 10 per minute |
| Search | `/v1/media` (browse and search) | 60 per minute |

The allowance is also the burst: a client starts with a full bucket that refills steadily, so the
auth default is ten immediately and then one more every six seconds. **Streaming and download are
deliberately never limited** — a player legitimately issues a burst of range requests, and limiting
it would break seeking.

**What to do.** Wait for `Retry-After`. Operators: raise `BEAM_RATE_LIMIT_AUTH_PER_MINUTE` or
`BEAM_RATE_LIMIT_SEARCH_PER_MINUTE`. If every user shares one bucket because they arrive through a
proxy, set `BEAM_RATE_LIMIT_TRUST_FORWARDED_FOR=true` — but only behind a proxy that **overwrites**
`X-Forwarded-For`, since a proxy that appends lets a client forge the header and evade the limit.

### metrics-unavailable

**503.** `GET /metrics` was called and no metrics recorder is installed.

**What to do.** Enable metrics in the server configuration. This is a 503 rather than a 404 so that
a scrape can tell "not enabled" from "wrong URL".

### internal

**500.** A server fault. Always Beam's problem, never the caller's.

**What to do.** Nothing client-side. Read the server log around the timestamp: a 500's `detail` is
deliberately terse and the log line carries the real cause. The usual causes are PostgreSQL being
unreachable and a schema/migration mismatch. On the artwork route it also covers a stored provider
URL that Beam refuses to fetch -- enrichment wrote it, so it is Beam's data rather than a provider
fault, and it is *not* [`artwork-upstream-failed`](#artwork-upstream-failed). Worth
[reporting](/help/support/) if none of these applies.

## Responses with no code

Some responses carry `"type": "about:blank"`. That is not an omission — RFC 9457 uses it to mean the
status code is the whole story, and for each of these there is no finer distinction Beam could draw.

| Status | When | What to do |
|---|---|---|
| `400` | A path or query parameter, header, cookie or body could not be parsed | Fix the request |
| `401` | No session cookie, or one the server does not recognise | Sign in |
| `404` | The URL matches no route at all | Check the path |
| `405` | A real path, wrong method | Check the method |
| `415` / `422` | Unsupported request media type, or a body that does not satisfy the schema | Fix the request |
| `416` | The requested byte range cannot be satisfied | See below |

### 416 Range Not Satisfiable

From `/v1/files/{id}/stream`, `/download`, and `/v1/artwork/{kind}/{id}/{variant}` — every response
Beam serves through its range engine: the range starts past the end of the representation, is
inverted, or **the representation is zero bytes**, which is refused whether or not a range was asked
for.

**What to do.** Check the file's size on disk first — a zero-byte file is usually a failed copy or a
broken symlink. Otherwise this is typically a player working from a stale cached length, so
hard-reload; if it persists, the file changed since it was indexed and the library needs a rescan.

## The one endpoint that does not use this shape

`GET /v1/health` answers **both** `200` and `503` with the full health object rather than a problem
document, because a monitor needs the per-dependency `checks` in either case. A `503` there means a
dependency is unhealthy — in practice, the database.

## Stability

- **`type` and `status` are the contract.** Branch on `type`; fall back to `status`.
- **`detail` is not.** It is diagnostic text and it will change.
- A code is never repurposed. If a condition splits into two, the new one gets a new code.

<Aside type="caution" title="Native clients see only the codes they were built with">
The Android and Apple apps decode `type` against the codes the server declared when the app was
built. A code added later — or a `429` from a proxy in front of Beam rather than from Beam — reaches
an older app as an unreadable response rather than as its status, until the client generator can
fall back ([getkono/spargen#268](https://github.com/getkono/spargen/issues/268)). Web clients read the
body directly and are unaffected.
</Aside>
