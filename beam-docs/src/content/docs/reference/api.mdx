Beam exposes one versioned REST API under `/v1`. The web app is built entirely on it, and it is
designed so that other clients could be too.

## Interactive documentation

A running server serves browsable API docs:

```
http://<your-server>:8000/openapi
```

The OpenAPI document itself is at `/api-doc/openapi.json`. It is generated from the server's own
handler definitions rather than maintained by hand, so it cannot drift from the implementation.

## Authentication

The API authenticates with the **session cookie** and nothing else.

- No API keys, no bearer tokens, no personal access tokens.
- **No credential is ever accepted in a URL or query string**, including on stream and download
  URLs. That is deliberate: URLs end up in logs, history and referrer headers.
- The browser never receives an OIDC token. Beam performs the whole flow server-side.

The practical consequence for anything scripted: you cannot obtain a long-lived token. A client
has to complete a browser sign-in and hold the resulting cookie.

## Sources, tracks and subtitles

`GET /v1/media/{id}/sources` is where a movie's or an episode's files are described, as the `items`
of a single, complete page: primary first,
each with its video, audio and subtitle tracks by stream index and with FFmpeg's own codec names
(`h264`, `eac3`, `subrip`, `hdmv_pgs_subtitle`). Subtitle files beside a video appear as tracks
with a `url` to fetch them as stored and, for SubRip and WebVTT, a `webvtt_url` to fetch them as
WebVTT. Every URL in a source is relative to the server and authenticated by the session cookie
like any other request.

Each source also names the tracks to start on for the signed-in user:
`default_audio_track_index` is a position in `audio_tracks` and `default_subtitle_track_index` a
position in `subtitle_tracks`, both counted from 0, the subtitle one absent to start without
subtitles. They follow the user's language preferences, which `GET /v1/me/language-preferences`
reads and `PUT` replaces whole: `audio_languages` and `subtitle_languages`, each most preferred
first and at most 16, and a `subtitle_mode` -- `off`, `forced_only` (the forced track in the
audio's language, for a film's foreign-language dialogue; the default) or `on` (full subtitles in
the first preferred language a source carries). A language is sent as `en`, `eng`, `English` or
`en-GB` alike and answered as the code tracks carry, `eng`. With no preference that a source can
meet, the file's own default track is chosen.

## Watched state

Progress is kept per movie and per episode, not per file. `PUT /v1/files/{file_id}/progress`
reports a position in whichever file is playing, and the answer is the title's state: `played`,
`position_secs` (where to resume; `0` once watched to the end), `play_count`, `last_played_at`, and
the `last_file_id` last played. `GET /v1/media/{id}/progress` reads the same for a movie or an
episode, and `DELETE` clears the position. `PUT` and `DELETE /v1/media/{id}/watched` mark a movie,
an episode, a season or a whole show watched or unwatched.

`GET /v1/continue-watching` returns one row per movie and one per show — a show's row being the
episode to resume or start next — and `GET /v1/history` pages through everything watched, newest
first, with `first` and `after`. Both carry each row's title, artwork and episode numbers, and the
`file_id` to play. The continue-watching row takes no cursor: it looks through at most the 1,000
titles played most recently, and its `page_info.has_next_page` says whether it left any unexamined.
`DELETE /v1/continue-watching/{id}` takes a title off the row until it is next played. Detail responses carry a `user_state` for the movie, or for the show and each season and
episode; `GET /v1/episodes/{id}` and `GET /v1/seasons/{id}` describe one episode (with its show and
the episodes either side) or one season.

## Watchlist, favourites and collections

`PUT /v1/watchlist/{id}` puts a movie or a show on the signed-in user's watchlist and
`DELETE /v1/watchlist/{id}` takes it off; `/v1/favourites/{id}` does the same for favourites. Both
answer `204`, and both are idempotent: a title already on the list keeps its place. A season or an
episode is refused with `not-a-title` -- the lists hold whole titles. `GET /v1/watchlist` and
`GET /v1/favourites` page through a list, newest addition first, with `first` and `after`; each
item is the title as browse lists it, with when it was added. A movie's or show's detail says
whether it is on each list, as `user_state.in_watchlist` and `user_state.in_favourites`.

Collections are the groupings a metadata provider makes of movies, such as a franchise: TMDB's
"collection". A movie's detail names the one it is in as `collection`; `GET /v1/collections` lists
every collection one of the library's movies is in, by name, and `GET /v1/collections/{id}` lists
its movies in release order. They fill in as movies are enriched.

## Library access and content ratings

An administrator decides what each user sees. `GET /v1/admin/users/{id}/access` reads a user's
access and `PUT` replaces it whole: `all_libraries`, or the `library_ids` granted, and a
`max_content_rating` -- an age band from `all_ages` to `adult` that the US film and TV
certifications fall into (`parental_guidance` takes `PG` and `TV-PG`, `teen` takes `PG-13` and
`TV-14`, and so on). A user nobody restricted sees every library with no maximum.

For a restricted user, browse, continue-watching, history and the library list hold only what they
may see, and any route given the id of something else -- a title, its seasons and episodes, its
files, subtitles and artwork -- answers `404` exactly as for an id that does not exist. Under a
maximum rating, a title with no certification Beam recognises is hidden. A movie's or show's
`content_rating` is the provider's certification, absent while none is known.

## Real-time updates

Administrative events — scan progress, enrichment outcomes — are delivered over **Server-Sent
Events** at `/v1/admin/events/stream`, authenticated by the same session cookie. There are no
WebSockets.

Missed events are not replayed. A client that reconnects should re-fetch current state rather than
assume continuity.

## Errors

Every failure is an RFC 9457 problem document whose `type` identifies it. Read [the error
reference](/reference/errors/) before writing any client error handling.

## Stability

<Aside type="note">
The API is pre-alpha and may change without a deprecation period until `/v1` is frozen. [API
stability and versioning](/reference/api-stability/) sets out what Beam will promise from then on:
which changes it may make within `/v1`, which ones need a `/v2`, and how a version is retired.
Native clients are tracked under [#78](https://github.com/justin13888/beam/issues/78).
</Aside>
