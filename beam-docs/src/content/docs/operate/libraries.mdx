A library is a directory Beam indexes. You can have several.

## Beam never writes to your media

The indexer only ever reads. It does not rename, move, delete, or write sidecar files, and it
never creates artwork next to your videos — enrichment data lives in Beam's database. The
[`.nfo` files and subtitles](#nfo-files-container-tags-and-subtitles) beside your videos are read,
never written, and a folder Beam may not write to indexes exactly like one it may.

The Compose file mounts your media read-only (`:ro`), so the guarantee is enforced by the container
runtime rather than resting on Beam's behaviour alone. Keep it that way if you write your own
Compose file or run the container another way: Beam needs no write access to a library root.

## Adding and scanning

Use **Add Library** on the Libraries page. The path is the path **inside the container**.

Each library shows its scan state: **Scanning…** while one runs, otherwise how long ago the last
one finished, or **Not scanned**. Progress streams live.

Scans are incremental — a file whose size and modification time are unchanged is skipped, so a
rescan of a large library is far cheaper than the first one. On Linux and macOS a file must also
still be the same file on disk (its inode and change time), so two files of one size swapped
between names are still told apart even when a copy kept their modification times. On a network
share only the change time is compared, not the inode, and on sshfs and rclone mounts not even that
(see [below](#network-shares-and-the-watch-limit)). A file whose permissions or owner changed is read
once, on the next scan, and skipped again after that. A filesystem watcher also picks up
changes as they happen — or within a poll interval, for a library on a network share (see
[below](#network-shares-and-the-watch-limit)) — so routine additions usually need no manual scan.

Scanning and enrichment are independent: a scan makes files playable, and metadata arrives
separately. See [Metadata and artwork](/operate/metadata/).

### One scan at a time

A scan is a job that runs in the background: asking for one returns at once, and the scan's
progress — how many files it has handled of how many, and what became of them — streams to the
admin page. A library is scanned by one job at a time, whatever started it: you, the scan at
startup, or the periodic rescan. Asking for a scan while one is running is refused with
[library-scan-in-progress](/reference/errors/#library-scan-in-progress); the periodic rescan simply
skips a library that is already being scanned. While a scan runs, changes the watcher sees in that
library wait for it to finish and are then picked up. Deleting a library while it is being scanned
stops the scan after the file it is on and waits for it — up to 30 seconds — before the library is
removed; the scan ends as cancelled. A scan still waiting its turn is cancelled at once, and
nothing new starts on a library once its deletion has begun. If the deletion then fails, the
library is scanned and watched again as before.

Beam keeps the latest scan of each library in memory. A restart forgets it — the library's *last
scanned* time is kept — and a scan running when the server stops is not resumed; the next periodic
rescan covers it.

### Files still being copied in

A file is indexed only once it has gone `BEAM_SCAN_SETTLE_SECS` (30 seconds by default) without
being written to. A film being copied onto the share is written for as long as the copy runs, so
it is left alone until the copy has finished: Beam does not read a half-copied file, and does not
probe a container whose index is written last. It appears about half a minute after the copy
finishes — the watcher comes back to it — and a scan that meets it mid-copy counts it as
*deferred*, not failed or missing. Set `BEAM_SCAN_SETTLE_SECS=0` to index files on sight.

## Where a library can live

Each library root must be **disjoint** from every other library and from Beam's data directory
(`BEAM_DATA_DIR`). Beam refuses to register a root that is the same directory as an existing
library, lies inside one, or contains one — that would index the same files twice, as two libraries
— and answers [library-path-overlaps-library](/reference/errors/#library-path-overlaps-library).
A root that overlaps the data directory is refused as
[library-path-overlaps-data-dir](/reference/errors/#library-path-overlaps-data-dir): Beam writes
there, and it must never write under a library. Paths are compared after symlinks and `..` are
resolved, by whole path components, so `/videos/movies` and `/videos/movies2` do not overlap.

The same rules are checked against the libraries you already have each time Beam starts. If
`BEAM_DATA_DIR` has been moved inside a library (or a library lies inside it), Beam refuses to start
and says so: move `BEAM_DATA_DIR` outside every library root. Two existing libraries that overlap
each other, registered before Beam refused that, keep working; Beam logs a warning naming both, and
deleting one and registering a disjoint root clears it.

## Symbolic links are not followed

When Beam walks a library — to scan it, when the watcher reports a change, or when it polls — it
never follows a symbolic link beneath the library root, to a file or to a directory. A link is
simply not part of the library: a symlinked video is not indexed, and a symlinked folder is not
descended into. Nor is a link followed at any component beneath the root when Beam reads a file: an NFO
it parses, a video or subtitle it measures, a video it hashes and probes while indexing, or a video
or subtitle it delivers. Nothing is ever recorded from a file that a link leads to. A file, or a
folder above it, replaced by a link since the walk is treated as missing -- at once, or, if the scan
already had that folder open, by the next scan, which finds the link. This keeps every file Beam
reads, records or serves inside the root you registered (the root itself may be a link) and rules
out link cycles. Measuring a file does not open it: a scan opens only the videos it hashes or
probes, so rescanning an unchanged library opens none of them, except a video Beam holds no
duration for (one whose earlier probe failed, say), which is probed again.

If you relied on symlinks before, a file that was indexed through a link is now
[missing](#when-files-go-missing): hidden, with its progress kept, until the grace period ends. To
bring media from elsewhere into a library, use a **bind mount** (another Compose volume under
`BEAM_VIDEO_DIR`, or `mount --bind` on the host) or a **hard link**; both are ordinary files and
directories to Beam.

## Network shares and the watch limit

The filesystem watcher uses native change events (inotify on Linux). Two situations defeat them,
and Beam handles both by **polling** the affected library instead — walking it every
`BEAM_WATCH_POLL_INTERVAL_SECS` (five minutes by default) — with no setting to change:

- **Network filesystems.** NFS, SMB/CIFS, 9p, Ceph and other network or FUSE filesystems (sshfs,
  rclone, mergerfs among them) do not raise events for changes made by another machine. Beam checks
  each library root's filesystem type when it starts watching it, and polls those that are on one.
  A local FUSE filesystem is polled too, because it cannot be told apart from a remote one.
  Scans of such a library stay incremental: they compare a file's size, modification time and
  change time, but not its inode number, which these filesystems may renumber after a remount or a
  cache eviction (rclone, SMB mounted with `noserverino`). Comparing it would read the whole library
  on every periodic rescan. sshfs and rclone mounts report a file's modification time as its change
  time, so on those two a swap of files of one size between names is missed when the copy kept
  their modification times, exactly as it would be by size and modification time alone. NFS and SMB
  report a real change time and are unaffected.
- **The watch limit.** On Linux each watched directory uses one of the per-user inotify watches
  (`fs.inotify.max_user_watches`). A library with more directories than remain is polled instead,
  whether the limit is hit when Beam starts watching it or later, as folders are added. Raise the
  limit on the host — for example `sysctl fs.inotify.max_user_watches=524288`, persisted in
  `/etc/sysctl.d/` — and restart Beam to watch those libraries natively again.

When a library starts being polled — when Beam first watches a network share, or moves a library
past the watch limit — Beam scans it once, so files added before polling began (such as the new
season whose folder could not get a watch) are not left waiting for the periodic rescan. At
startup, Beam sets up every watch before its startup scan begins, so that scan is the one a share
polled from the start gets — it is not scanned twice — and polling begins once the startup scan
has finished. A new library starts being watched as soon as it is added — in the background, so
adding a large network share does not wait for Beam to walk it — and a deleted one stops being
watched or polled as soon as it is deleted. A library Beam could not start watching, or could not
move to polling, is tried again after the next `BEAM_SCAN_INTERVAL_SECS` interval and its rescan.
Watching a new library does not index what is already in it: scan it, or wait for the periodic
rescan.

The admin status endpoint (`GET /v1/admin/status`, field `watcher`) reports, for every library,
whether it is watched natively, polled (and why), or not watched at all, together with the watch
limit and whether it has been reached. The periodic rescan (`BEAM_SCAN_INTERVAL_SECS`) remains the
backstop for all of them.

## When files go missing

A file that is gone from disk is not removed at once. Beam marks it **missing**: it drops out of its
title's sources and cannot be streamed, and a title with no other file drops out of continue-watching
and history — but Beam keeps its record. Every viewer's resume point belongs to the title, not the
file, so it is kept either way. A movie or show whose files are **all** missing drops out
of browsing and search at once, since it has nothing to play; its own page still opens, so a
bookmark does not break. If the file comes back at the same path, the next scan (or the filesystem
watcher) restores it exactly as it was, progress included, and the title is listed again.

A missing file is removed for good only when a scan still cannot find it after a grace period — 30
days unless `BEAM_MISSING_FILE_GRACE_DAYS` says otherwise (see
[Configuration](/reference/configuration/)). Removing it keeps everyone's progress on its title;
only the note of which file they last played is forgotten.
Set the grace to `0` to remove missing files at the next scan. A title left with no files at all
is removed by the same scan, together with its metadata; the scan's completion entry in the admin
log counts it under `titles_removed`. A scan that could not read the whole library removes no
titles.

Two things never count as a file going missing:

- **Part of the library could not be read.** If a scan cannot list a folder, or cannot check a
  file it listed — a permissions problem, a flaky network share — the files beneath that path are
  left exactly as they were, and the scan writes a warning to the admin log naming it. The rest of
  the library is scanned as normal, so files elsewhere can still be marked missing or removed.
- **The whole library went away.** A watcher event while the library root is unavailable changes
  nothing, and a root that holds **no video files at all** — none with an extension listed
  [below](#which-files-get-indexed), counting files Beam skips by their name (samples, trailers,
  your ignore patterns) — while the library still has video files indexed is refused outright.
  Files inside a folder Beam skips wholesale (a hidden or housekeeping folder, a disc structure, an
  extras folder, a folder an ignore pattern matches) are never looked at, so they do not count: a root holding only
  `Movie (2019)/Trailers/Teaser.mkv` is refused too. A refused scan changes nothing, so this errs
  on the safe side. That is what an unmounted volume looks like, whether its mount point is left empty or
  holds only a sentinel or hidden file such as `.not_mounted` or `.DS_Store` — see
  [Scan refused: library root is empty](/help/troubleshooting/#scan-refused-library-root-is-empty).

<Aside type="note" title="A library spread over several disks">
If a library root holds several mount points and only **one** of them is unmounted, the root still
contains videos from the others, so the empty-root refusal does not apply. The unmounted disk's
files are marked missing instead — hidden, not removed — and come back with their progress when the
disk is remounted, as long as that happens within the grace period. For a disk that is routinely
offline for longer, raise `BEAM_MISSING_FILE_GRACE_DAYS`, or give it a library of its own.
</Aside>

To remove every video from a library on purpose, delete the library.

## Renaming and moving files

Rename a file, move it to another folder, or rename a whole folder — a season folder from `S01` to
`Season 1`, say — and Beam recognises the file by its contents rather than indexing it as new. It
keeps the same record, so everyone's resume point, its place in its movie or show, and its audio
and subtitle tracks all follow it, and it is not probed again. This works whether the watcher sees
the move as it happens or the next scan finds it, and for a file moved out of the library and back
in, as long as it comes back within the grace period. Subtitle files and NFOs beside it are matched
by where they are now: a moved video has the subtitles beside its new name, and an NFO moved with it
keeps pinning its title to the same id — or, if the admin log said its id was not used because the
title already had another, still leaves that pin alone. An NFO you edit on the way re-pins the title
to the id it now names — and a `movie.nfo` or `tvshow.nfo` that several moved videos share is judged
for all of them together, so it makes no difference which of them Beam comes to first. An NFO
already in the folder a video is moved into is not taken by that video when Beam has already read
it for the files there; one Beam has not read yet is applied as a new file's NFO would be, keeping
the title's pin if it names another id. If Beam saw an NFO deleted, putting it back in the same
place is adding it, and it re-pins its title; if it comes back with its video in another place, it
is that video's NFO arriving with it, and the pin stays.

The same holds when files trade names. Swap two files' names, rotate three, or rename a file onto
the name of one you deleted earlier, and each record follows its file's contents rather than its
old name — your place in *Heat* stays with *Heat*. NFOs follow in the same way: swap two folders,
or rotate three, and each NFO counts as moved rather than edited, so one whose id the admin log
said was not used still leaves the pin alone, however the folders' names sort. Only an NFO whose
contents you also changed on the way re-pins its title. The watcher sees such a change one name at a
time and cannot tell which file is which yet, so it leaves those files — the videos and the NFOs
beside them — as they were, and the next scan sorts them out; scan the library to have it done at
once. If a file takes over the name of one whose contents are nowhere in the library any more, that
old record is kept as missing, not deleted, and goes after the grace period like any other missing
file.

One exception keeps a common habit working: replacing a film you have been watching by renaming
another file onto its name — a better copy downloaded beside it, say. When someone has played the
file whose name is taken, its contents are not still somewhere else in the library (as they would be
after a swap of two names), and nobody has played the file renamed onto it, Beam keeps the watched
record at that name, with everyone's resume point, and treats the new contents as a change to it.
The renamed file's own record is marked missing, like any file that is gone.

What counts as the same file:

- **The same contents, in the same library.** Beam compares a hash of the whole file and its size,
  so a file you re-encoded or edited is a different file. A file moved to another library is new
  there.
- **The old copy is gone.** Copying a file leaves the original in place, so the copy is a new file
  — and Beam writes an info entry to the admin log noting the duplicate.
- **Two identical files moved at once** keep their own records, matched by file name, then by
  folder. When that still does not tell them apart — one of two identical copies moved and the
  other deleted, say — the record someone has watched most recently wins, and failing that Beam
  picks the same one every time.

Each move is written to the admin log as an info entry naming the old and new paths, and a scan's
progress counts the files it recognised as moved. Beam still never renames or moves anything
itself: it only follows what you do.

A moved file keeps the title it had, even if its new name points at a different one — renaming
`Heat (1995).mkv` to `Ronin (1998).mkv` leaves it a file of *Heat*. Beam treats a move as the same
file, not a new one to classify.

## Which files get indexed

Beam indexes video files with these extensions, case-insensitively, and nothing else:

```
mp4  mkv  avi  mov   webm  m4v  ts   m2ts  mts
flv  wmv  3gp  ogv   mpg   mpeg divx  asf  f4v
```

Subtitles, `.nfo` files, artwork and anything else beside your videos are not indexed as videos:
they are not hashed, probed or listed as titles. Beam does read two kinds of them — `.nfo` files and
text subtitles — as described [below](#nfo-files-container-tags-and-subtitles). (A Beam version
before this recorded every file under a library root; the first scan after upgrading marks those
records [missing](#when-files-go-missing), so the scan's "marked missing" count is large once, and
they are removed when the grace period ends.)

Some video files are skipped too, because they are not what a library is for:

- **Hidden files and folders** — any name starting with `.`, at any depth.
- **NAS and system housekeeping folders** — `@eaDir` (Synology), `#recycle`, `$RECYCLE.BIN`,
  `System Volume Information`, `lost+found`.
- **DVD and Blu-ray disc structures** — everything in a `VIDEO_TS`, `AUDIO_TS`, `BDMV` or
  `CERTIFICATE` folder, at any depth. A disc copied whole splits one film into files such as
  `VTS_01_1.VOB` or `00001.m2ts`, none of which is a title on its own, so Beam does not index them
  yet. Remux the disc to a single file (`Heat (1995)/Heat (1995).mkv`) to add it to your library.
- **Extras folders** anywhere below the top of a library — `Extras`, `Featurettes`,
  `Behind The Scenes`, `Deleted Scenes`, `Interviews`, `Sample`, `Samples`, `Bonus`
  (`Breaking Bad/Extras/`, a release folder's `Sample/`).
- **`Trailers`, `Shorts`, `Scenes` and `Other` folders** inside a title's folder. These names can
  also mean a collection, so they are skipped only in a folder naming a title and year
  (`Movie (2019)/Trailers/`), a season folder (`Show/Season 1/Scenes/`), or any folder below the
  top level (`TV/Show/Trailers/`). A top-level folder without a year is taken for a category, so
  `Movies/Trailers/` and a top-level `Shorts/` are collections, and are indexed.
- **Files named as extras** — a name ending in `-trailer`, `-sample`, `.sample`, `_sample`,
  `-featurette`, `-behindthescenes`, `-deleted` or `-interview`, or a file called just `sample` or
  `trailer`.
- **Your own ignore patterns** — set `BEAM_SCAN_IGNORE` to comma-separated glob patterns, matched
  case-insensitively against the path relative to the library root: `Downloads,**/*.partial.mkv`.
  `*` stops at a `/` and `**` crosses it; a pattern that matches a folder skips everything in it,
  so `Downloads/*` — which matches each folder in `Downloads` too — skips all of it.
  Patterns live in Beam's configuration, never in files written into your library. See
  [Configuration](/reference/configuration/).

A file that was indexed and is now skipped — you added a pattern, or renamed a file to
`-sample` — is marked missing, like a deleted file.

## How Beam decides what a file is

Beam reads the file's **path inside the library**, folders included, not just its name. Names are
cleaned first: `.` and `_` become spaces, `[...]` and `{...}` groups are dropped, and a title stops
at the first release-noise token — resolutions, sources, codecs and release tags such as `1080p`,
`WEB-DL`, `BluRay`, `x265`, `AAC`, `Atmos`, `PROPER`, `EXTENDED`, `REMUX`.

A file is a **TV episode** when its path gives it an episode number, in any of these forms:

| Form | Example | Season, episode |
|---|---|---|
| `SxxEyy` | `Show.S01E02.mkv`, `show s1e2.mkv`, `Show.S01.E02.mkv` | 1, 2 |
| `1x02` | `Show.1x02.mkv` | 1, 2 |
| Air date | `The.Daily.Show.2024.03.01.mkv`, `Show 2024-03-01.mkv` | 2024, 301 (the year, and `MMDD`) |
| Absolute number | `[Group] Show - 012 [1080p].mkv`, `E12.mkv` | 1 (or the season folder's), 12 |
| In a season folder only | `Season 5/Episode 1.mkv`, `Season 5/Ep 1.mkv`, `Season 5/501 - Title.mkv` | 5, 1 |

A three- or four-digit number such as `501` counts only in a season folder, and only when its
leading digits are that folder's season: `Season 5/601.mkv` is not an episode. Outside a season
folder, `Show.101.mkv` is a movie.

Everything else is a **movie** — with four exceptions, each indexed without a title, as an unknown
file, with a warning in the admin log naming it:

- a file **in a season folder** with no episode number (`Show/Season 01/Behind the Scenes.mkv`). It
  is clearly part of a show, and guessing it into a movie would invent a film;
- a file **in a folder that is only a range of seasons** with no season and episode marker
  (`Show/Season 1-2/Episode 1.mkv`). It is part of the show above, but the range cannot say which
  season;
- a fansub-style `<title> - <number>` that no folder names as a show — at the top of a library, or
  in a folder spelling the show differently (`Frieren (2023)/[SubsPlease] Sousou no Frieren - 12
  (1080p).mkv`). Read as a movie, a season would become dozens of films. Name the folder as the
  files do, or put them in a season folder;
- a fractional `<title> - <number>.<digit>` (`Show - 12.5.mkv`), a recap or special between two
  episodes. It has no episode number of its own, and reading it as episode 12 would put it beside
  the real one.

Absolute numbers are read only where the layout makes them unambiguous — typically anime. The file
must be in a folder, and either that folder is a season folder, or the title before the number
names the same show as the folder (`Show (1998)/Show - 012.mkv`). The `<title> - <number>` form also
needs a season folder or a number of at least two digits: `Movie (2019)/Movie (2019) - 1.mkv` is a
movie, but `Chernobyl (2019)/Chernobyl (2019) - 01.mkv` is an episode. A four-digit year is an
episode number only in a season folder of the show the title names
(`One Piece (1999)/Season 1/One Piece - 1999.mkv`); elsewhere it is the release year.

If a name carries more than one marker, the real one is the **last before the release noise**:
`Show.S01E01.1080p.WEB-S00E00.mkv` is S01E01. A multi-episode file — `S01E01E02`, `S01E01-E03`,
`S01E01-03`, or markers written back to back such as `S01E01.S01E02` — belongs to its **first**
episode and records the range it runs to.

### Titles and years

- A **movie**'s title and year come from its filename: `Movie.Name.2019.2160p.WEB-DL.x265-GROUP.mkv`
  is *Movie Name* (2019). A title that is itself a year still works: `1917.2019.mkv` is *1917*
  (2019), and `Blade.Runner.2049.2017.mkv` is *Blade Runner 2049* (2017). A release word that
  opens a title is part of it: `Uncut.Gems.2019.mkv` is *Uncut Gems*.
- A movie's **folder** fills in what its filename leaves out: `Kill Bill (2003)/Kill Bill.mkv` takes
  the folder's year, since the folder names the same title, and a filename that is nothing but
  release noise (`Movie (2019)/1080p.BluRay.x264.mkv`) takes the folder's title too. The top of a
  library is never a folder for this.
- An **episode**'s title is the text **after** its marker: `Show.S01E02.The.Title.1080p.mkv` is
  titled *The Title*. With nothing there it is *Episode 2* until metadata enrichment names it.
- A **show**'s year is the one in its folder (`Doctor Who (2005)`), or a year right before the
  marker in the filename (`Show.2019.S01E02.mkv`). A filename that is only a year keeps it as the
  title: `1923.S01E01.mkv` is the show *1923*.

### Movie editions

A film can have several editions in one library, each listed separately. Beam reads the edition
from a Plex/Jellyfin tag — `Movie (2019) {edition-Final Cut}.mkv` — or, failing that, from edition
words after the title or its year (`Movie (2019) Director's Cut.mkv`): *Director's Cut* (or `DC`), *Extended*, *Theatrical*, *Unrated*, *Uncut*,
*IMAX*, *Remastered*, *Special Edition*, *Ultimate*, *Final Cut*, *Criterion*, *Anniversary*.
`Movie.2019.Extended.Remastered.1080p.mkv` is the *Extended, Remastered* edition. Every copy of the
same edition — a 1080p and a 4K file — is a version of that one edition (see
[Multiple versions](#multiple-versions)).

### Multi-part movies

A film split across files is one movie, not one per file:

```
Movies/
└── Movie (2019)/
    ├── Movie (2019) - CD1.avi
    └── Movie (2019) - CD2.avi
```

Beam reads a part from the end of the name: `cd`, `disc`, `disk`, `part` or `pt` and a number,
after a space, dot, dash or underscore — `- CD1`, `- Part 2`, `.pt1`, `_disc_1`. Only release
details such as `1080p` or a `[GROUP]` tag may follow it. `part` and `pt` count only after the
year in the file name itself (`Movie (2019) - Part 1.mkv`); the folder never makes them a part, so
`Movie (2019)/Movie - Part 1.mkv` is a film of its own until it is renamed
`Movie (2019) - Part 1.mkv`. That is because some titles end in them: *Harry Potter and the
Deathly Hallows Part 1 (2010)* and *The Hunger Games Mockingjay Pt 1* are films of their own, and
one folder may hold two films, as `Che (2008)/Che Part 1.mkv` and `Che Part 2.mkv` do, or a sequel
filed beside its predecessor, as `The Godfather (1972)/The Godfather Part 2.mkv` is. A number that
opens the name (`Part 2: The Sequel (2020).mkv`) or is followed by more of the title is part of the
title. A file in an extras folder (`Extras/`, `Trailers/`) is never a part.

The parts of one edition in one folder are one version of the movie, listed in part order, and its
size and length are all the parts' together. Parts of different editions — `{edition-Director's
Cut} - CD1` — are a version of that edition. The parts must run from 1 with no gap: if two files
in one folder claim the same part, or the folder has parts 2 and 3 but no part 1, or parts 1 and 3
but no part 2, Beam cannot play them as one film, so it lists each of that folder's parts as a
version of its own.

A library indexed by an earlier Beam, which listed each part as a film (*Movie - CD1*, *Movie -
CD2*), is merged on the first scan after the upgrade: the films become one, named *Movie*, and
every file keeps its watch progress. A title a provider matched or you renamed keeps its name. Two
titles a provider matched to different films are never merged, even when their names now read as
one: both are kept as they were, and the admin log names the pair so you can rename the files or
correct a match. Once one title's match is corrected to the other's film, the two are merged the
next time Beam starts, and each part keeps its place in the movie.

The web player and the apps start a multi-part version at its first part; they do not yet move on
to the next part by themselves.

### Directory layout for TV

A show is named by its **series folder**:

- In a **season folder** the show is the season folder's parent. A season folder is any folder
  whose name carries a season word and number — `Season 01`, `Series 2`, `Saison 3`, `Staffel 4`,
  `Temporada 5`, and also `Breaking Bad Season 1`, `Season 1 (2008)`, `Season 01 - Pilot Season`
  — or a lone `S06` with no episode after it, or `Specials` (season 0).
- A **box set** folder above the season folders — the show's name followed only by `The`,
  `Complete`, `Series` or `Collection`, such as `Firefly The Series Collection`, or only those
  words, such as `The Complete Series` — names the show its files name (*Firefly*).
- A **season pack** folder such as `The.Office.US.S02.1080p.BluRay` is a season folder too. The
  text before its season token names the show when there is no series folder above it, or when the
  folder above names something else (a category such as `TV`).
- A **multi-season pack** folder — a range of seasons after the show's name, such as
  `Breaking.Bad.S01-S05.COMPLETE.1080p`, `Breaking.Bad.S01-05`, `Breaking Bad Seasons 1-5` or
  `Breaking Bad Seasons 1 to 5` — is named by the text before the range (*Breaking Bad*). It is
  not a season folder: each file's own marker, or the `Season N` folder inside the pack, gives the
  season. A folder that is **only** a range — `Season 1-2`, `Seasons 1 to 10`, `Complete S01-S05`
  — is a pack inside its series folder, which names the show and its year, as a season folder's
  parent does: `Friends (1994)/Season 1-10/Friends.S03E05.mkv` is *Friends* (1994).
- Otherwise the show is the folder the episode is in — unless the filename names a different show.
  `TV Shows/Breaking.Bad.S01E01.mkv` is *Breaking Bad*, not *TV Shows*; `Breaking Bad
  (2008)/Breaking.Bad.S01E01.mkv` is the folder's *Breaking Bad* (2008).
- An episode at the top of a library, or in a season folder at the top, takes its show's name from
  its filename; with none there it belongs to a show called *Unknown Show*.

Both common layouts work, and name the same show:

<FileTree>
- videos
  - movies
    - Movie Name (2019)
      - Movie.Name.2019.1080p.BluRay.x264.mkv
      - Movie.Name.2019-trailer.mkv (skipped)
    - Another.Film.2021.2160p.WEB-DL.x265.mkv
  - shows
    - Breaking Bad
      - Season 01
        - Breaking.Bad.S01E01.Pilot.1080p.mkv
        - Breaking.Bad.S01E02.1080p.mkv
      - Specials
        - Breaking.Bad.S00E01.mkv
    - Better Call Saul
      - Better.Call.Saul.S01E01.mkv
</FileTree>

When a filename's season disagrees with its season folder — `Season 01/Show.S02E05.mkv` — the
filename wins, and the server log says so.

### NFO files, container tags and subtitles

What a media manager (Kodi, tinyMediaManager, Jellyfin, Emby) or an encoder left beside or inside a
video is read too — never written.

**NFO files.** Beam reads the Kodi-style `.nfo` describing a video: `<file name>.nfo` beside it,
else `movie.nfo` in its folder, and for an episode `tvshow.nfo` in its folder or the series folder
above a season folder. A `movie.nfo` or `tvshow.nfo` at the very top of a library is ignored — it
would describe everything. An NFO may be XML (`<movie>`, `<tvshow>`, one `<episodedetails>` per
episode of a multi-episode file), just a provider URL (`https://www.themoviedb.org/movie/603`), or
XML followed by a URL.

- **An NFO decides what the file is.** A `<movie>` NFO makes a movie of a file whose name looks
  like an episode, and an `<episodedetails>` with a season and episode makes an episode of one
  whose name does not — `Lost/Pilot Part One.mkv` beside a `Pilot Part One.nfo` for season 1,
  episode 1 is that episode of *Lost*. Its `<edition>` names the movie's edition.
- **An NFO names a new title.** Its `<title>` and `<year>` are what a movie or show is shown as
  until enrichment replaces them. Files are still [grouped](#multiple-versions) by the name their
  path parses to, never by an NFO's title.
- **An NFO's provider id pins the title.** A `<uniqueid>` (the `default="true"` one first), a
  legacy `<id>`, `<tmdbid>` or `<imdbid>`, or a provider URL, pins the movie or show to that id, in
  the order TMDB, AniList, IMDb, TheTVDB. A second file whose NFO names the same id joins the same
  title whatever its name, and [enrichment](/operate/metadata/#pinned-titles) fetches the title by
  that id instead of searching for it. An episode's own ids never pin its show; `tvshow.nfo` does.
  When two NFOs pin one title to different ids, the first pin is kept and the admin log says so.

An NFO added or edited after its video was indexed re-pins the title at the next scan, or as soon
as the watcher sees it (unless a video beside it is being moved, swapped or replaced at the same
time: then the next scan applies it) — whatever modification time it carries, so one copied in
with `cp -p` or `rsync -a` counts too. Only the files an NFO actually describes are re-pinned: a `movie.nfo`
leaves alone a video that has its own `<file name>.nfo`, and an NFO at the top of the library, in a
category folder above your show folders (`TV/tvshow.nfo` above `TV/Lost/`), or more than one folder
above an episode, pins nothing. An NFO that describes several titles — a `movie.nfo` in a folder
of two movies, a `tvshow.nfo` in a folder holding episodes of two shows — pins only one of them,
the same one every time,
since an id pins one title, and the admin log says so once. Deleting an NFO leaves its title
pinned; putting an NFO back is adding one, and pins the title to the id it names — as long as Beam
saw it gone, whether you deleted the NFO or a folder holding it (the watcher reported the deletion,
or a scan ran while it was missing). One put back unseen with the same contents is taken as
unchanged. An NFO larger than 1 MiB, one that is not UTF-8, one declaring a document
type, and one that is a symbolic link are ignored, and the file is classified by its path.

**Container tags.** The tags inside a file fill only what its path leaves open. An MP4 tagged with
a show, season and episode (`show`, `season_number`, `episode_sort`) is that episode even when its
name has no marker (`The Office/The Dundies.m4v`); a file in a season folder whose name has no
episode number takes the episode from its tag; a `title` tag names an episode that has no title of
its own, unless it is release noise or just the filename; a `date` or `year` tag gives a movie with
no year one. A tag never overrides what the path or an NFO says, and a `title` or `show` tag
longer than 512 bytes is cut to that.

**Subtitles.** A text subtitle — `.srt`, `.vtt`, `.ass` or `.ssa` — named after its video is
recorded as a subtitle of that video, with the language and flags its name gives:

| File | Language | Flags / title |
|---|---|---|
| `Movie (1999).en.srt`, `Movie (1999).eng.srt`, `Movie (1999).English.srt` | English | |
| `Movie (1999).en.forced.srt` | English | forced |
| `Movie (1999).en.sdh.srt`, `.en.cc.srt`, `.en.hi.srt` | English | SDH |
| `Movie (1999).hi.srt` | Hindi | |
| `Movie (1999).pt-BR.vtt` | Portuguese | titled *pt-BR* |
| `Movie (1999).Commentary.en.srt` | English | titled *Commentary* |
| `Movie (1999)/Subs/English.srt` | English | (the only video in `Movie (1999)/`) |

Languages are recognised as two- or three-letter codes or English names. A subtitle belongs to the
video whose name it starts with — the longest, so `Movie.Extended.en.srt` belongs to
`Movie.Extended.mkv`, not `Movie.mkv` — and a `Subs` or `Subtitles` folder beside the videos holds
subtitles named the same way, or named for their language alone when the folder above holds one
video. Image subtitles (`.sub`/`.idx`, `.sup`) are not indexed. Rescans and the watcher keep the
list current as subtitles are added, changed and removed. Each indexed subtitle is listed as a
track of its video and served read-only, as stored and — for `.srt` and `.vtt` up to 8 MiB — as
WebVTT for browsers; nothing is ever written beside your videos. The players do not show subtitles
yet: see [Watching](/using/watching/#subtitles).

### Upgrading: files are reclassified once

These rules are versioned. When Beam starts with newer rules than a file was classified under, the
next scan reclassifies the file from its path — it keeps its record, and with it everyone's
progress; nothing is re-probed. A show a Beam version before these rules named after a season folder
(*Season 01*) has its episodes moved to the show its series folder names, and the emptied
*Season 01* show is removed by the same scan. The first scan after upgrading to a Beam that reads
[NFO files](#nfo-files-container-tags-and-subtitles) reclassifies every file this way, so the NFOs
already in your library take effect — and pin their titles — without a manual rescan. Container
tags are read when a file is probed and kept with it, so a later reclassification places the file
by them too. A file last probed by a Beam version before that is reclassified without its tags
until its content changes and it is probed again.

The name each movie and show is [grouped by](#multiple-versions) is versioned with the rules too.
Before the scan reclassifies anything, Beam works out each title's grouping name again from its
files, so a title keeps its record — its artwork, description, genres, provider match and
everyone's progress — when the rules now spell its name differently (`Grey's Anatomy` and a scene
release's `Greys.Anatomy` group together since these rules). When two titles now group under one
name, they become one: the one matched to a provider (else the older) is kept, and the other's
files and episodes join it. The admin Logs tab lists what was updated and merged.

If Beam cannot work the grouping names out — the database refused, say — the admin Logs tab says
so, and until it succeeds no file is reclassified: every title keeps its files and its provider
match, while new files are indexed as usual. The next scan tries again.

## Multiple versions

Movies are grouped by their **cleaned title and year** (and [edition](#movie-editions)). Index two
files that clean to the same title and year and Beam treats them as two sources of one movie, and viewers get a picker labelled
with each one's resolution and codec. The comparison ignores case, accents on Latin, Greek and
Cyrillic letters, and punctuation, and reads `&` as `and`: `Amelie.2001.mkv` and
`Amélie (2001).mkv` are one movie. That includes marks some languages count as separate letters:
`ñ` matches `n`, `ä` matches `a` and `й` matches `и`, so `Мой (2010)` and `Мои (2010)` are one
movie. Marks in other scripts, such as a Japanese voicing mark or a Devanagari vowel sign, still
count: `かぎ` and `かき` are two titles. Shows are grouped
the same way by the name the [TV layout](#directory-layout-for-tv) gives them — usually the
**series folder name** (and a year in it, such as `Doctor Who (2005)`).

The grouping comes from the filenames and never changes afterwards. When metadata enrichment gives
a title the provider's name, later files still join it under the name their filename parses to.

Episodes are grouped by **show, season and episode number**. Two files of the same show that
both parse as, say, `S01E01` — `Show.S01E01.1080p.mkv` beside `Show.S01E01.720p.mkv` — are two
sources of one episode, with the same picker.

This is how Beam serves constrained connections: put a smaller re-encode beside the original.
It is also the fix when a file will not play in a browser — add an H.264/AAC MP4 version.

Two limits to know:

- **The year is part of the grouping key.** `Dune.1984.mkv` and `Dune.2021.mkv` are two movies, as
  they should be — but so are `Dune.2021.mkv` and a `Dune.mkv` with no year, unless it sits in a
  `Dune (2021)` folder. Give every version of a film the same year in its name or its folder.
- **The first file names the episode.** An episode's title and runtime come from the first file
  indexed for it (or from metadata enrichment since). A later version's filename never renames it.

## When a scan reports failures

A file is recorded as failed when Beam cannot read its size, cannot hash it, or cannot store the
result — a permissions problem or unreadable storage. The rest of the scan continues regardless;
one bad file never aborts it.

A file Beam *can* read but cannot probe is **not** a failure. It is indexed with unknown status and
counted as added, so a corrupt or truncated video shows up as an unplayable unknown file rather
than in the scan's failure count. Every later scan tries to probe it again, and the first time a
probe succeeds — the file was repaired, or finished copying — it is sorted into its movie or show
like any new file, keeping its record. The same goes for a file that probed before but whose new
content does not: it keeps its movie or show, is marked changed, and loses the old content's
duration and streams until a later scan probes it successfully.
