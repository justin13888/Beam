A library is a directory Beam indexes. You can have several.

## Beam never writes to your media

The indexer only ever reads. It does not rename, move, delete, or write sidecar files, and it
never creates artwork next to your videos — enrichment data lives in Beam's database.

The Compose file mounts your media read-only (`:ro`), so the guarantee is enforced by the container
runtime rather than resting on Beam's behaviour alone. Keep it that way if you write your own
Compose file or run the container another way: Beam needs no write access to a library root.

## Adding and scanning

Use **Add Library** on the Libraries page. The path is the path **inside the container**.

Each library shows its scan state: **Scanning…** while one runs, otherwise how long ago the last
one finished, or **Not scanned**. Progress streams live.

Scans are incremental — a file whose size and modification time are unchanged is skipped, so a
rescan of a large library is far cheaper than the first one. A filesystem watcher also picks up
changes as they happen — or within a poll interval, for a library on a network share (see
[below](#network-shares-and-the-watch-limit)) — so routine additions usually need no manual scan.

Scanning and enrichment are independent: a scan makes files playable, and metadata arrives
separately. See [Metadata and artwork](/operate/metadata/).

## Where a library can live

Each library root must be **disjoint** from every other library and from Beam's data directory
(`BEAM_DATA_DIR`). Beam refuses to register a root that is the same directory as an existing
library, lies inside one, or contains one — that would index the same files twice, as two libraries
— and answers [library-path-overlaps-library](/reference/errors/#library-path-overlaps-library).
A root that overlaps the data directory is refused as
[library-path-overlaps-data-dir](/reference/errors/#library-path-overlaps-data-dir): Beam writes
there, and it must never write under a library. Paths are compared after symlinks and `..` are
resolved, by whole path components, so `/videos/movies` and `/videos/movies2` do not overlap.

The same rules are checked against the libraries you already have each time Beam starts. If
`BEAM_DATA_DIR` has been moved inside a library (or a library lies inside it), Beam refuses to start
and says so: move `BEAM_DATA_DIR` outside every library root. Two existing libraries that overlap
each other, registered before Beam refused that, keep working; Beam logs a warning naming both, and
deleting one and registering a disjoint root clears it.

## Symbolic links are not followed

Beam never follows a symbolic link beneath a library root — to a file or to a directory — when it
scans, when the watcher reports a change, or when it polls. A link is simply not part of the
library: a symlinked video is not indexed, and a symlinked folder is not descended into. This keeps
every indexed file inside the root you registered (the root itself may be a link) and rules out
link cycles.

If you relied on symlinks before, a file that was indexed through a link is now
[missing](#when-files-go-missing): hidden, with its progress kept, until the grace period ends. To
bring media from elsewhere into a library, use a **bind mount** (another Compose volume under
`BEAM_VIDEO_DIR`, or `mount --bind` on the host) or a **hard link**; both are ordinary files and
directories to Beam.

## Network shares and the watch limit

The filesystem watcher uses native change events (inotify on Linux). Two situations defeat them,
and Beam handles both by **polling** the affected library instead — walking it every
`BEAM_WATCH_POLL_INTERVAL_SECS` (five minutes by default) — with no setting to change:

- **Network filesystems.** NFS, SMB/CIFS, 9p, Ceph and other network or FUSE filesystems (sshfs,
  rclone, mergerfs among them) do not raise events for changes made by another machine. Beam checks
  each library root's filesystem type when it starts watching it, and polls those that are on one.
  A local FUSE filesystem is polled too, because it cannot be told apart from a remote one.
- **The watch limit.** On Linux each watched directory uses one of the per-user inotify watches
  (`fs.inotify.max_user_watches`). A library with more directories than remain is polled instead,
  whether the limit is hit when Beam starts watching it or later, as folders are added. Raise the
  limit on the host — for example `sysctl fs.inotify.max_user_watches=524288`, persisted in
  `/etc/sysctl.d/` — and restart Beam to watch those libraries natively again.

When a library starts being polled — when Beam first watches a network share, or moves a library
past the watch limit — Beam scans it once, so files added before polling began (such as the new
season whose folder could not get a watch) are not left waiting for the periodic rescan. At
startup, Beam sets up every watch before its startup scan begins, so that scan is the one a share
polled from the start gets — it is not scanned twice — and polling begins once the startup scan
has finished. A deleted library stops being watched or polled, and a library Beam could not move
to polling is watched again, after the next `BEAM_SCAN_INTERVAL_SECS` interval and its rescan.

The admin status endpoint (`GET /v1/admin/status`, field `watcher`) reports, for every library,
whether it is watched natively, polled (and why), or not watched at all, together with the watch
limit and whether it has been reached. The periodic rescan (`BEAM_SCAN_INTERVAL_SECS`) remains the
backstop for all of them.

## When files go missing

A file that is gone from disk is not removed at once. Beam marks it **missing**: it drops out of its
title's sources, continue-watching and history, and cannot be streamed — but Beam keeps its record,
and with it every viewer's resume point. A movie or show whose files are **all** missing drops out
of browsing and search at once, since it has nothing to play; its own page still opens, so a
bookmark does not break. If the file comes back at the same path, the next scan (or the filesystem
watcher) restores it exactly as it was, progress included, and the title is listed again.

A missing file is removed for good only when a scan still cannot find it after a grace period — 30
days unless `BEAM_MISSING_FILE_GRACE_DAYS` says otherwise (see
[Configuration](/reference/configuration/)). Removing it also removes everyone's progress for it.
Set the grace to `0` to remove missing files at the next scan. A title left with no files at all
is removed by the same scan, together with its metadata; the scan's completion entry in the admin
log counts it under `titles_removed`. A scan that could not read the whole library removes no
titles.

Two things never count as a file going missing:

- **Part of the library could not be read.** If a scan cannot list a folder, or cannot check a
  file it listed — a permissions problem, a flaky network share — the files beneath that path are
  left exactly as they were, and the scan writes a warning to the admin log naming it. The rest of
  the library is scanned as normal, so files elsewhere can still be marked missing or removed.
- **The whole library went away.** A watcher event while the library root is unavailable changes
  nothing, and a root that holds **no video files at all** — none with an extension listed
  [below](#which-files-get-indexed), counting files Beam skips by their name (samples, trailers,
  your ignore patterns) — while the library still has video files indexed is refused outright.
  Files inside a folder Beam skips wholesale (a hidden or housekeeping folder, a disc structure, an
  extras folder, a folder an ignore pattern matches) are never looked at, so they do not count: a root holding only
  `Movie (2019)/Trailers/Teaser.mkv` is refused too. A refused scan changes nothing, so this errs
  on the safe side. That is what an unmounted volume looks like, whether its mount point is left empty or
  holds only a sentinel or hidden file such as `.not_mounted` or `.DS_Store` — see
  [Scan refused: library root is empty](/help/troubleshooting/#scan-refused-library-root-is-empty).

<Aside type="note" title="A library spread over several disks">
If a library root holds several mount points and only **one** of them is unmounted, the root still
contains videos from the others, so the empty-root refusal does not apply. The unmounted disk's
files are marked missing instead — hidden, not removed — and come back with their progress when the
disk is remounted, as long as that happens within the grace period. For a disk that is routinely
offline for longer, raise `BEAM_MISSING_FILE_GRACE_DAYS`, or give it a library of its own.
</Aside>

To remove every video from a library on purpose, delete the library.

## Which files get indexed

Beam indexes video files with these extensions, case-insensitively, and nothing else:

```
mp4  mkv  avi  mov   webm  m4v  ts   m2ts  mts
flv  wmv  3gp  ogv   mpg   mpeg divx  asf  f4v
```

Subtitles, `.nfo` files, artwork and anything else beside your videos are left alone: they are not
hashed, probed or given a record. (A Beam version before this recorded every file under a library
root; the first scan after upgrading marks those records [missing](#when-files-go-missing), so the
scan's "marked missing" count is large once, and they are removed when the grace period ends.)

Some video files are skipped too, because they are not what a library is for:

- **Hidden files and folders** — any name starting with `.`, at any depth.
- **NAS and system housekeeping folders** — `@eaDir` (Synology), `#recycle`, `$RECYCLE.BIN`,
  `System Volume Information`, `lost+found`.
- **DVD and Blu-ray disc structures** — everything in a `VIDEO_TS`, `AUDIO_TS`, `BDMV` or
  `CERTIFICATE` folder, at any depth. A disc copied whole splits one film into files such as
  `VTS_01_1.VOB` or `00001.m2ts`, none of which is a title on its own, so Beam does not index them
  yet. Remux the disc to a single file (`Heat (1995)/Heat (1995).mkv`) to add it to your library.
- **Extras folders** anywhere below the top of a library — `Extras`, `Featurettes`,
  `Behind The Scenes`, `Deleted Scenes`, `Interviews`, `Sample`, `Samples`, `Bonus`
  (`Breaking Bad/Extras/`, a release folder's `Sample/`).
- **`Trailers`, `Shorts`, `Scenes` and `Other` folders** inside a title's folder. These names can
  also mean a collection, so they are skipped only in a folder naming a title and year
  (`Movie (2019)/Trailers/`), a season folder (`Show/Season 1/Scenes/`), or any folder below the
  top level (`TV/Show/Trailers/`). A top-level folder without a year is taken for a category, so
  `Movies/Trailers/` and a top-level `Shorts/` are collections, and are indexed.
- **Files named as extras** — a name ending in `-trailer`, `-sample`, `.sample`, `_sample`,
  `-featurette`, `-behindthescenes`, `-deleted` or `-interview`, or a file called just `sample` or
  `trailer`.
- **Your own ignore patterns** — set `BEAM_SCAN_IGNORE` to comma-separated glob patterns, matched
  case-insensitively against the path relative to the library root: `Downloads,**/*.partial.mkv`.
  `*` stops at a `/` and `**` crosses it; a pattern that matches a folder skips everything in it,
  so `Downloads/*` — which matches each folder in `Downloads` too — skips all of it.
  Patterns live in Beam's configuration, never in files written into your library. See
  [Configuration](/reference/configuration/).

A file that was indexed and is now skipped — you added a pattern, or renamed a file to
`-sample` — is marked missing, like a deleted file.

## How Beam decides what a file is

Beam reads the file's **path inside the library**, folders included, not just its name. Names are
cleaned first: `.` and `_` become spaces, `[...]` and `{...}` groups are dropped, and a title stops
at the first release-noise token — resolutions, sources, codecs and release tags such as `1080p`,
`WEB-DL`, `BluRay`, `x265`, `AAC`, `Atmos`, `PROPER`, `EXTENDED`, `REMUX`.

A file is a **TV episode** when its path gives it an episode number, in any of these forms:

| Form | Example | Season, episode |
|---|---|---|
| `SxxEyy` | `Show.S01E02.mkv`, `show s1e2.mkv`, `Show.S01.E02.mkv` | 1, 2 |
| `1x02` | `Show.1x02.mkv` | 1, 2 |
| Air date | `The.Daily.Show.2024.03.01.mkv`, `Show 2024-03-01.mkv` | 2024, 301 (the year, and `MMDD`) |
| Absolute number | `[Group] Show - 012 [1080p].mkv`, `E12.mkv` | 1 (or the season folder's), 12 |
| In a season folder only | `Season 5/Episode 1.mkv`, `Season 5/Ep 1.mkv`, `Season 5/501 - Title.mkv` | 5, 1 |

A three- or four-digit number such as `501` counts only in a season folder, and only when its
leading digits are that folder's season: `Season 5/601.mkv` is not an episode. Outside a season
folder, `Show.101.mkv` is a movie.

Everything else is a **movie** — with three exceptions, each indexed without a title, as an unknown
file, with a warning in the admin log naming it:

- a file **in a season folder** with no episode number (`Show/Season 01/Behind the Scenes.mkv`). It
  is clearly part of a show, and guessing it into a movie would invent a film;
- a fansub-style `<title> - <number>` that no folder names as a show — at the top of a library, or
  in a folder spelling the show differently (`Frieren (2023)/[SubsPlease] Sousou no Frieren - 12
  (1080p).mkv`). Read as a movie, a season would become dozens of films. Name the folder as the
  files do, or put them in a season folder;
- a fractional `<title> - <number>.<digit>` (`Show - 12.5.mkv`), a recap or special between two
  episodes. It has no episode number of its own, and reading it as episode 12 would put it beside
  the real one.

Absolute numbers are read only where the layout makes them unambiguous — typically anime. The file
must be in a folder, and either that folder is a season folder, or the title before the number
names the same show as the folder (`Show (1998)/Show - 012.mkv`). The `<title> - <number>` form also
needs a season folder or a number of at least two digits: `Movie (2019)/Movie (2019) - 1.mkv` is a
movie, but `Chernobyl (2019)/Chernobyl (2019) - 01.mkv` is an episode. A four-digit year is an
episode number only in a season folder of the show the title names
(`One Piece (1999)/Season 1/One Piece - 1999.mkv`); elsewhere it is the release year.

If a name carries more than one marker, the real one is the **last before the release noise**:
`Show.S01E01.1080p.WEB-S00E00.mkv` is S01E01. A multi-episode file — `S01E01E02`, `S01E01-E03`,
`S01E01-03`, or markers written back to back such as `S01E01.S01E02` — belongs to its **first**
episode and records the range it runs to.

### Titles and years

- A **movie**'s title and year come from its filename: `Movie.Name.2019.2160p.WEB-DL.x265-GROUP.mkv`
  is *Movie Name* (2019). A title that is itself a year still works: `1917.2019.mkv` is *1917*
  (2019), and `Blade.Runner.2049.2017.mkv` is *Blade Runner 2049* (2017). A release word that
  opens a title is part of it: `Uncut.Gems.2019.mkv` is *Uncut Gems*.
- A movie's **folder** fills in what its filename leaves out: `Kill Bill (2003)/Kill Bill.mkv` takes
  the folder's year, since the folder names the same title, and a filename that is nothing but
  release noise (`Movie (2019)/1080p.BluRay.x264.mkv`) takes the folder's title too. The top of a
  library is never a folder for this.
- An **episode**'s title is the text **after** its marker: `Show.S01E02.The.Title.1080p.mkv` is
  titled *The Title*. With nothing there it is *Episode 2* until metadata enrichment names it.
- A **show**'s year is the one in its folder (`Doctor Who (2005)`), or a year right before the
  marker in the filename (`Show.2019.S01E02.mkv`). A filename that is only a year keeps it as the
  title: `1923.S01E01.mkv` is the show *1923*.

### Movie editions

A film can have several editions in one library, each listed separately. Beam reads the edition
from a Plex/Jellyfin tag — `Movie (2019) {edition-Final Cut}.mkv` — or, failing that, from edition
words after the title or its year (`Movie (2019) Director's Cut.mkv`): *Director's Cut* (or `DC`), *Extended*, *Theatrical*, *Unrated*, *Uncut*,
*IMAX*, *Remastered*, *Special Edition*, *Ultimate*, *Final Cut*, *Criterion*, *Anniversary*.
`Movie.2019.Extended.Remastered.1080p.mkv` is the *Extended, Remastered* edition. Every copy of the
same edition — a 1080p and a 4K file — is a version of that one edition (see
[Multiple versions](#multiple-versions)).

### Directory layout for TV

A show is named by its **series folder**:

- In a **season folder** the show is the season folder's parent. A season folder is any folder
  whose name carries a season word and number — `Season 01`, `Series 2`, `Saison 3`, `Staffel 4`,
  `Temporada 5`, and also `Breaking Bad Season 1`, `Season 1 (2008)`, `Season 01 - Pilot Season`
  — or a lone `S06` with no episode after it, or `Specials` (season 0).
- A **box set** folder above the season folders — the show's name followed only by `The`,
  `Complete`, `Series` or `Collection`, such as `Firefly The Series Collection` — names the show
  its files name (*Firefly*).
- A **season pack** folder such as `The.Office.US.S02.1080p.BluRay` is a season folder too. The
  text before its season token names the show when there is no series folder above it, or when the
  folder above names something else (a category such as `TV`).
- Otherwise the show is the folder the episode is in — unless the filename names a different show.
  `TV Shows/Breaking.Bad.S01E01.mkv` is *Breaking Bad*, not *TV Shows*; `Breaking Bad
  (2008)/Breaking.Bad.S01E01.mkv` is the folder's *Breaking Bad* (2008).
- An episode at the top of a library, or in a season folder at the top, takes its show's name from
  its filename; with none there it belongs to a show called *Unknown Show*.

Both common layouts work, and name the same show:

<FileTree>
- videos
  - movies
    - Movie Name (2019)
      - Movie.Name.2019.1080p.BluRay.x264.mkv
      - Movie.Name.2019-trailer.mkv (skipped)
    - Another.Film.2021.2160p.WEB-DL.x265.mkv
  - shows
    - Breaking Bad
      - Season 01
        - Breaking.Bad.S01E01.Pilot.1080p.mkv
        - Breaking.Bad.S01E02.1080p.mkv
      - Specials
        - Breaking.Bad.S00E01.mkv
    - Better Call Saul
      - Better.Call.Saul.S01E01.mkv
</FileTree>

When a filename's season disagrees with its season folder — `Season 01/Show.S02E05.mkv` — the
filename wins, and the server log says so.

### Upgrading: files are reclassified once

These rules are versioned. When Beam starts with newer rules than a file was classified under, the
next scan reclassifies the file from its path — it keeps its record, and with it everyone's
progress; nothing is re-probed. A show a Beam version before these rules named after a season folder
(*Season 01*) has its episodes moved to the show its series folder names, and the emptied
*Season 01* show is removed by the same scan.

## Multiple versions

Movies are grouped by their **cleaned title and year** (and [edition](#movie-editions)). Index two
files that clean to the same title and year and Beam treats them as two sources of one movie, and viewers get a picker labelled
with each one's resolution and codec. The comparison ignores case, accents on Latin, Greek and
Cyrillic letters, and punctuation, and reads `&` as `and`: `Amelie.2001.mkv` and
`Amélie (2001).mkv` are one movie. That includes marks some languages count as separate letters:
`ñ` matches `n`, `ä` matches `a` and `й` matches `и`, so `Мой (2010)` and `Мои (2010)` are one
movie. Marks in other scripts, such as a Japanese voicing mark or a Devanagari vowel sign, still
count: `かぎ` and `かき` are two titles. Shows are grouped
the same way by the name the [TV layout](#directory-layout-for-tv) gives them — usually the
**series folder name** (and a year in it, such as `Doctor Who (2005)`).

The grouping comes from the filenames and never changes afterwards. When metadata enrichment gives
a title the provider's name, later files still join it under the name their filename parses to.

Episodes are grouped by **show, season and episode number**. Two files of the same show that
both parse as, say, `S01E01` — `Show.S01E01.1080p.mkv` beside `Show.S01E01.720p.mkv` — are two
sources of one episode, with the same picker.

This is how Beam serves constrained connections: put a smaller re-encode beside the original.
It is also the fix when a file will not play in a browser — add an H.264/AAC MP4 version.

Two limits to know:

- **The year is part of the grouping key.** `Dune.1984.mkv` and `Dune.2021.mkv` are two movies, as
  they should be — but so are `Dune.2021.mkv` and a `Dune.mkv` with no year, unless it sits in a
  `Dune (2021)` folder. Give every version of a film the same year in its name or its folder.
- **The first file names the episode.** An episode's title and runtime come from the first file
  indexed for it (or from metadata enrichment since). A later version's filename never renames it.

## When a scan reports failures

A file is recorded as failed when Beam cannot read its size, cannot hash it, or cannot store the
result — a permissions problem or unreadable storage. The rest of the scan continues regardless;
one bad file never aborts it.

A file Beam *can* read but cannot probe is **not** a failure. It is indexed with unknown status and
counted as added, so a corrupt or truncated video shows up as an unplayable unknown file rather
than in the scan's failure count.
